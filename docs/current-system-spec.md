# 📝 Karukan 現行仕様と改善検討メモ

確認日: 2026-10-11 / 対象: ローカル作業ツリー（HEAD `cd62fb0`＋今回の変更）

**現在のコードを基準にした仕様整理です。** 実装上の仕様と改善案を分けて記載しています。インストール済みアプリの設定・辞書内容・実測性能は調査していません。以下の設定値はリポジトリの既定値です。

## 🎯 1. システムの目的と範囲

Karukanは、macOS向けのローマ字入力式日本語IMEです。ニューラルかな漢字変換を中心に、辞書・修正学習・表記変換ルールを組み合わせます。

- 入力中に変換結果と候補を更新するライブ変換に対応します。
- ライブ変換と文節単位の修正変換を備えます。ライブ変換のOFF設定はありません。ライブ候補を選び、必要に応じて文節単位の修正へ進めます。
- 明示的に修正した部分を、周囲の文脈とともに学習します。
- 英字、数字、記号、絵文字の候補も扱います。
- Swiftフロントエンドの対象はmacOS 13以降です。かな入力レイアウトは実装されていません。

macOSへ登録する入力モードは**日本語のみ**です。通常の英数入力はOSの英語入力ソースへ切り替えます。Shift+英字によるエンジン内部の英字モードは、OSの入力ソースとは別の機能です。

## 🏗️ 2. 全体構成

```text
入力先アプリ
    ↕ キーイベント・未確定文字列・確定文字列・周辺テキスト
KarukanIME（Swift / InputMethodKit）
    ↕ 改行区切りJSON-RPC 2.0 / stdin・stdout
karukan-imserver（Rust / karukan-im）
    ├─ 入力状態・読み・カーソル・候補・文節・修正学習
    └─ 推論ワーカー（モデル1個、ライブ変換と明示変換を直列実行）
           ↕
karukan-engine
    ├─ ローマ字変換
    ├─ llama.cpp / jinenモデル
    ├─ システム辞書・ユーザー辞書・辞書ラティス
    ├─ 文節修正学習
    └─ 表記・数字・記号・絵文字の候補生成
```

| 構成要素 | 責務 |
|---|---|
| `karukan-engine` | 変換・辞書・学習などの基礎機能です。 |
| `karukan-im` | キー操作を解釈し、入力状態と画面更新指示を管理します。 |
| `karukan-macos` | macOSとの接続、未確定文字列・候補画面の表示、子プロセス管理を行います。 |
| `karukan-cli` | 辞書作成・取り込み・閲覧、HTTP変換サーバー、精度評価を提供します。 |

**macOS版IMEは、CLIのHTTPサーバーを経由しません。** 同梱のRust子プロセスを利用します。モデル学習は別プロジェクトの`karukan-jinen`で行います。

## ⌨️ 3. 入力状態と操作

状態は `Empty（未入力）→ Composing（入力中）→ Conversion（候補選択中）` です。確定すると未入力状態へ戻ります。

読みとカーソル位置の基準データはRustの`InputBuffer`です。表示用の変換文字列は読みとは別に保持します。

| 操作 | 現在の動作 |
|---|---|
| ローマ字入力 | ひらがなへ変換し、未確定文字列を更新します。 |
| Enter | 入力中の表示または選択した変換結果を確定します。 |
| Space / Tab / ↓ | Escによる一時停止中は全文のライブ変換を再開します。通常は全文候補の選択へ進み、その後は次候補へ移動します。 |
| ↑ | 前候補へ移動します。入力中の候補選択にも使います。 |
| 全文候補の最後から次へ | 文節単位の修正へ移行します。 |
| ← / → | 入力中は読みのカーソル移動、変換中は文節移動です。 |
| Shift+← / Shift+→ | 変換中の文節境界を縮小・拡大します。 |
| 1〜9 | 変換中は現在の候補を適用します。全文の確定はEnterです。 |
| Esc | 全文をひらがなに戻し、ライブ変換を一時停止します。追加入力またはSpaceで再開します。 |
| Backspace / Delete | 入力中の文字を削除します。変換中のBackspaceには専用処理があります。 |
| F6 / F7 / F8 | ひらがな・全角カタカナ・半角カタカナとして確定します。 |
| Shift+英字 | エンジン内部の英字モードへ入ります。 |
| Shift+Space | 全角スペースを入力します。文節変換中は選択中の文字列を確定して全角スペースを続けます。 |
| JISかな | ひらがな入力へ戻します。 |
| JIS英数 | 未確定文字列を確定し、OS側の英数切り替えへキーを渡します。 |
| Command併用の操作 | Swift側で入力先アプリへ渡します。 |

Page Up/Down、F9/F10、Ctrl併用キーにはIMEの操作を割り当てません。候補画面は表示専用で、マウスクリックでは選択しません。

未入力のひらがな状態でSpaceを押すと、半角スペースを確定します。フォーカスが外れた際も未確定文字列を確定します。

右Command単独タップについては、現行Swiftコードにタップ判定器は見当たりません。**Karabinerなどで右CommandをJISかなへ割り当てた場合に、かなキーとして処理する構成です。**

## ⚡ 4. 入力中の変換

### 🔄 非同期処理

入力中の推論は専用ワーカーで行います。キー処理では読みと表示を更新し、推論待ちの間は前回変換済みの部分に新しい読みをつないで表示します。

- 未開始のライブ変換要求は、最新の1件へ置き換えます。
- 実行中の推論を途中で中断する仕組みはありません。
- 完了結果は、キャンセル世代・入力状態・読みの前方一致を確認して適用します。
- 入力が末尾へ追加されただけなら、旧結果を変換済みの前半として利用できます。
- Swiftは未確定文字列がある間、**50ms間隔**で結果を問い合わせます。同時に複数の問い合わせを実行しないよう制御します。

ライブ変換のOFF設定はありません。Escを押すと、全文をひらがなに戻して、その入力の変換を一時停止します。続きを入力すると再開し、最初のSpaceでは全文のライブ変換を開始して第一候補を表示します。旧設定ファイルの`live_conversion=false`は読み込み時に無視します。

### 🧩 内部チャンク

入力を、既定では最大**30文字**の内部チャンクへ分割します。日本語／非日本語の種別が変わる場所でも分割します。

| 文字種 | 扱い |
|---|---|
| ひらがな・カタカナ・漢字 | モデルへ送ります。 |
| 長音符`ー` | 読みの先頭の連続する長音符は変換せず保持します。単語内部の長音符は日本語側に含めます。 |
| 数字・英字・記号・句読点・中黒`・` | ライブ変換ではそのまま保持します。 |

例: `きょうは。あした123` は、日本語・句点・日本語・数字のチャンクに分かれます。画面では1本の未確定文字列として表示します。

各チャンクのモデル文脈は「編集欄の左側テキスト＋直前までのチャンクの変換結果」の末尾です。変更前後の共通部分を比較し、先頭・末尾の変更されていないチャンクを再利用します。

**内部チャンクと、ユーザーが修正する文節は別物です。** チャンクは推論量を抑えるための区切りです。

## 🧠 5. モデルと候補生成

### 🤖 推論モデル

| 項目 | 現行仕様 |
|---|---|
| 既定モデル | `jinen-v1-small-q5`、GPT-2 Small / 90M / Q5_K_Mです。 |
| 別の登録モデル | `jinen-v1-xsmall-q5`、GPT-2 XSmall / 26M / Q5_K_Mです。 |
| 実行方式 | llama.cppでローカルCPU推論を行います。GPU層数は0です。 |
| 入力 | 読みをカタカナへ変換し、左文脈と特殊トークンを付けたjinen形式です。 |
| トークナイザー | 外部の`tokenizer.json`を利用します。 |
| 候補生成 | 1候補ならgreedy、複数ならbeam searchです。 |
| 基礎的な上限 | llama.cppコンテキストは既定256トークン、生成は最大50トークンです。 |

変換処理はローカルで行います。モデル未取得時にはHugging Faceから取得します。インストール時の先行取得対象は、**設定で選択されたモデル**です。

### 📋 全文候補と文節候補

入力中に見せる全文候補は通常最大**3件**です。ライブ変換が有効な2〜6文字の短い読みでは、ひらがなを2番目、全角カタカナを3番目に追加し、最大5件になります。1文字のひらがなは読みを第1候補へ優先します。

Spaceを押した際、利用可能なら入力中の候補一覧をそのまま引き継ぎます。ライブ表示があって候補が複数ある場合、Spaceで2番目を選ぶ動作です。

ライブ候補を使い切ると文節修正へ移ります。**解析する表記はライブ変換の第一候補です。選択中の第二候補以降ではありません。** Linderaの内蔵IPADICで形態素解析し、元の読みに対応付けて区切ります。対応しない部分には近似的に読みを割り当て、解析できない場合は全体を1文節として扱います。

形態素解析は、①読み全体の変換が完了して✅が付いた時、または②第二候補以降を選び始めた時に、専用ワーカーで先行実行します。読み・第一候補の表記・世代で結果を識別し、古い結果を適用しません。

文節修正へ入る際は、各文節の第一候補を元の第一候補の部分文字列に固定します。学習・辞書・追加モデル候補はそれを置き換えません。解析が未完了の場合も、第一候補を1文節として即時表示し、完了後に文字列を変えず区切りを適用します。その短い準備期間中の候補移動・文節移動は消費し、入力先へ渡しません。

移行時は辞書・表記ルールの候補を用意し、各文節のモデル候補は非同期で追加します。追加の際も第一候補と現在の選択を維持します。文節境界を変更した後のモデル候補更新も非同期です。

候補の生成元は次のとおりです。

1. 文脈が適合する修正学習です。
2. ユーザー辞書です。
3. 全文モデル・辞書ラティス・分割モデル＋辞書の混合候補です。
4. システム辞書の完全一致候補です。
5. ひらがな・カタカナなどの代替候補と表記変換です。

③は、モデル1位→ラティス1位→混合1位→モデル2位…という**順位ベースの混合**です。モデルの対数確率と辞書コストを共通の尺度で比較する方式ではありません。重複する表記は除去します。

`num_candidates=9`は生成設定であり、入力中の全文候補の表示件数と同じではありません。候補画面は既定9件単位のページ表示です。

### 📚 辞書ラティスと長文処理

辞書ラティスは読みの各位置から辞書語をつなぎ、全文の候補を探索します。探索は区間候補5件・保持状態20件・最終候補9件に制限します。

混合候補では句読点を優先して分割し、その後は辞書ラティスの境界を利用し、最後に文字数上限で分割します。分割した日本語部分のモデル候補と辞書候補を組み合わせます。

**この分割経路があっても、候補再生成では先に全文モデル推論を実行します。** また、明示変換はワーカーの完了を同期で待ちます。入力中の候補を引き継げる場合は、この再生成を避けます。

### 🛡️ 読みの保護と表記補正

- かなだけのモデル出力は、幅・ひらがな／カタカナを正規化した後、読みが一致しないものを除外します。
- `〜`と`～`は同等として、個数の増減を許可しません。
- 漢字を含む出力などは、読みの曖昧さを考慮して保守的に通します。完全な読み一致保証はありません。
- `ず／づ`の読み替えを、元の読みを含め最大4通り試します。
- 末尾の未完了ローマ字`w`は、確定やライブ候補選択で失わないよう保持します。

## 🔤 6. 表記変換・絵文字

候補の表記変換は、主にユーザーが入力した読みを基に行います。モデルや辞書の全候補へ一律に派生候補を増やす方式ではありません。

| 機能 | 例・条件 |
|---|---|
| 英字 | 大文字・小文字・全角などを生成します。 |
| カタカナ | 半角カタカナを生成します。 |
| 記号 | 記号の別表記や、読みから記号への候補を生成します。 |
| 数字 | 数字だけの入力から全半角・漢数字・大字・丸数字・ローマ数字・基数表記などを生成します。値や長さによる制限があります。 |
| 日本語から絵文字 | `わらい`や`ぴえん`などから対応する絵文字を生成します。 |
| `:query`から絵文字 | 未入力状態で`:`を入力すると専用モードへ入り、英語名・別名・ローマ字名を検索します。 |

絵文字モードではローマ字かな変換・モデル・辞書・修正学習・文節変換を使いません。検索は部分列一致で、連続一致の長さ、一致位置、検索対象名の短さで順位付けします。候補は1ページ分です。

検索なしでは既定の9絵文字を表示します。一致候補がない場合は候補を表示せず、Enterで入力した文字列をそのまま確定できます。確定または検索文字列の消去で元の入力モードへ戻ります。

## 🧾 7. 修正学習

**通常のEnter確定や最初の候補の受け入れだけでは学習しません。** 選び直した候補と初期候補の差分から、変更した部分を記録します。絵文字は対象外です。

保存項目は、読み・選択した表記・左右の文脈ヒント・修正回数・最終記録時刻です。文脈ヒントには隣接文節や編集欄の端の文字を使用します。

- 読みは完全一致で照合します。以前の全文を前方一致で候補へ出しません。
- 文脈付きの記録は、その文脈が一致する場合に候補になります。
- 文脈なしの記録も利用できます。
- 基礎スコアは `10 / (1 + 経過日数) + ln(1 + 頻度)` です。左文脈一致で20、右文脈一致で30を加えます。
- 既定の上限は10,000件です。超過時は**最終記録時刻が古い順**に削除します。
- 入力ソースの非アクティブ化やサーバー終了時などに保存します。確定のたびには保存しません。
- 保存先は`segment_learning.tsv`です。旧`learning.tsv`は読み込みません。

現在の保存は対象ファイルを直接作成・上書きする方式です。テンポラリファイルからの置換はありません。

## ⚙️ 8. 設定・データ・文脈

基準ディレクトリは`~/Library/Application Support/com.karukan.karukan-im/`です。

| ファイル | 用途 |
|---|---|
| `config.toml` | ユーザー設定です。指定した項目を内蔵既定設定へ重ねます。 |
| `dict.bin` | システム辞書です。設定の`dict_path`で変更できます。 |
| `user_dicts/` | ユーザー辞書です。Mozc TSV／KRKN形式を自動判定し、ファイル名順に読み込んで統合します。 |
| `segment_learning.tsv` | 文節修正学習です。 |

| 設定 | 既定値 | 意味 |
|---|---|---|
| `live_num_candidates` | 3 | 入力中のモデル生成候補数です。 |
| `num_candidates` | 9 | 明示変換の生成候補数です。 |
| `use_context` | true | 左側の周辺テキストをモデル文脈へ利用します。 |
| `max_context_length` | 10 | モデルへ渡す文脈の最大文字数です。 |
| `composing_chunk_len` | 30 | 1チャンクの読みの上限です。 |
| `model` | `jinen-v1-small-q5` | ライブ・明示変換で共用するモデルです。 |
| `n_threads` | 4 | 推論スレッド数です。0はllama.cppの既定動作です。 |
| `learning.enabled` | true | 修正学習を有効にします。 |
| `learning.max_entries` | 10000 | 修正学習の保持上限です。 |

`EngineConfig`とユーザー設定から、ライブ変換のON/OFF項目を削除しています。

Swiftは未確定入力の開始前に、カーソル左側の最大40 UTF-16単位を取得します。Rust側は改行を越える文脈を切り、設定文字数へさらに短縮します。取得できなければ以前の文脈を消します。

**入力先アプリによって周辺テキストを取得できる範囲が異なります。** 通信仕様は左右の文脈を表現できますが、現在のSwift実装が取得するのは左側だけです。

設定や辞書の読み込みは起動・初期化時です。変更後の自動再読み込みはありません。設定読み込みに失敗するとサーバーは既定設定へ戻します。

## 🔌 9. 通信・障害時の動作

プロトコルはv2です。主なメソッドは`init`、`process_key`、`poll_live_conversion`、`select_candidate`、`commit`、`reset`、`set_surrounding_text`、`save_learning`、`status`です。

Rustは「キーを処理したか」と画面更新指示を返します。候補のクリック操作はありません。互換用の`select_candidate` RPCは残っていますが、Swiftの候補画面は呼び出しません。文字位置はUnicodeスカラー数で送信し、SwiftがmacOSのUTF-16位置へ変換します。

- キー処理のSwift側同期タイムアウトは3秒、確定は1秒です。
- キー処理の応答が得られない場合、通常の文字キーは入力先へ渡します。未確定文字列がある場合の特殊キーは消費し、AppKitの特殊文字が流入するのを防ぎます。
- 推論結果に含まれる制御文字・jinen内部トークン・AppKitの特殊キー文字を候補から除外します。古いポーリング応答は、入力セッションの世代と入力先を確認して破棄します。
- クラッシュ後は1・2・4・8・15秒…の待機で再起動します。正常な初期化で待機をリセットします。
- スリープ復帰時もRust子プロセスを再起動します。
- 正常終了はstdinを閉じ、学習保存と終了を待ちます。約2秒待っても終了しない場合は終了シグナルを使います。
- モデル初期化失敗はエラーです。システム辞書がない場合は辞書なしで動作できます。
- ログは`~/Library/Logs/KarukanIME/karukan-ime.log`です。通常のRustログレベルはinfoです。

## 🛠️ 10. 辞書作成・評価・配布

辞書はdouble-array trieを使用します。KRKN v1・v2を扱い、v2では出典・カテゴリ・説明などの情報を保持します。

一般語彙のMozc・Sudachi・JMdictと、地名系の日本郵便・JMnedict・国土地理院・SKKなどの取り込みツールがあります。ソースマニフェストはバージョン・URL・SHA-256・ライセンス・優先度を管理します。取り込み機能の存在は、インストール済み辞書に全ソースが含まれることを意味しません。

`make install`はアプリのビルド・配置、未配置の辞書取得、選択モデルの先行取得を行います。既存の`dict.bin`は上書きしません。

CLIのHTTPサーバーは既定で`127.0.0.1:3000`です。ローマ字変換・かな漢字変換・モデル一覧などのAPIとWeb UIを提供します。AJIMEE-Benchツールは完全一致率と文字誤り率を評価します。

テストはRustのエンジン・辞書・変換・プロトコル、Swiftのキー変換・通信・Rustサーバー統合などを含みます。今回の変更ではRust 306件・Swift 32件のテストと、karukan-imのClippyを通過しています。実測ベンチマークと実アプリでの手動入力確認は行っていません。

## 🔎 11. 問題点・改善点の検討材料

以下は**コードから確認した制約と、それに対する改善案**です。発生頻度や実際の影響は測定していません。

| 優先度の目安 | 確認した制約 | 改善案・確認方法 |
|---|---|---|
| 高 | 文節移行と文節候補更新は非同期化していますが、ライブ候補を引き継げない際の全文候補再生成には同期処理が残ります。モデルも共用します。 | 通常キー・全文候補選択・文節移行・境界調整の待ち時間を別々に計測します。特にp95／p99と最長時間を確認し、処理量の削減や段階的な候補表示を検討します。 |
| 高 | 長文でも、候補再生成では分割変換より先に全文モデル推論を実行します。 | 一定長以上で全文推論を省略する方式を比較します。トークン上限、文字欠落、応答時間への効果を確認します。 |
| 高 | Swiftの待機タイムアウトと、Rust側の処理中止は連動していません。 | タイムアウト後の遅延応答・キー通過・エンジン状態の関係を確認し、要求取消や再同期を設計します。 |
| 高 | 学習データは直接上書きします。確定ごとの保存もありません。 | 一時ファイル＋置換で保存を保護します。異常終了時に許容する学習損失を決め、定期保存やバックアップを検討します。 |

| 中 | モデル出力の読み保護は、漢字を含む表記などでは完全ではありません。 | 数字・英字・記号・助詞・固有名詞の保持率を評価します。辞書や形態素解析による検証を段階的に増やします。 |

| 中 | macOSから右文脈を取得していません。左文脈もアプリ依存です。 | Cocoa・Electron・ブラウザー・ターミナル別に取得率と変換品質を比較します。対応アプリでは右文脈の取得も検討します。 |

| 中 | 学習は文脈の完全一致に依存し、削除は最終記録時刻順です。 | 適用範囲が狭すぎないか、頻繁に修正した古い語が消えないかを確認します。学習の閲覧・削除UIも検討します。 |
